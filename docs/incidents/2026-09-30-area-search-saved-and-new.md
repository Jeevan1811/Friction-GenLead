# Incident: area searches omitted companies already in MSV's workbook

- **Symptom:** MSV searched Wacol and Pinkenba and expected businesses he had already collected in his workbook (including examples such as Allnex and Air Liquide) to appear alongside new candidates. The company list page still contained saved rows, but the area-search results showed only newly admitted prospects.
- **Cause:** global duplicate suppression correctly avoided inserting duplicate company rows but the research result model discarded those saved companies instead of presenting them as a distinct area-matched cohort.
- **Fix:** before public discovery, match existing Companies rows to their Locations by exact postcode, suburb/address text and the bundled postcode-place lookup. Company names are never used as location evidence. New public candidates remain independently deduplicated against Companies and Rejected. Search results, recent-run links and company filters distinguish “Already on your list” from “New prospects.”
- **Location safeguards:** exact postcode and place evidence must not contradict explicit state/country qualifiers. Wacol/4076, Pinkenba/4008, sibling-area exclusion, a postcode-only fallback and state/postcode conflict cases are covered by backend tests. The imported “Pure Environmental” example with postcode 4172 is not labeled a Wacol match solely because MSV mentioned it with Wacol; each saved match needs location evidence.
- **Map:** workbook rows, public-source prospects and unknown origins have distinct shapes/colors, mixed co-located origins use a split marker, and popups/legend explain the origin. Source metadata refresh rerenders markers without needing location rows to change.
- **Data safety:** the new `known_company_ids` SearchRuns column is appended at the end using the adapter's existing append-only header routine; existing columns/rows are not shifted or rewritten. Provider results only write the new-prospect cohort. No production search or prospect-row write was used in this release QA. The live header was not independently read back after process startup.
- **Verification:** 186 backend tests, 30 web unit tests, TypeScript check, optimized Next build and 7 Playwright browser tests passed. Browser fixtures and screenshots are synthetic. Production build passed; API health/login returned 200, unauthenticated Search redirected with 307, protected API returned 401, and only `frictiongenlead-api`/`frictiongenlead-web` were restarted. Production commit: `7b3b34a3eb0cf31b9230c933d2074f7f25683353` (PR #31).
- **Limits:** public-source coverage remains uneven and candidate discovery is not exhaustive. GitHub reported no CI checks; delegated secondary reviews were unavailable because the guarded Gemini lane was denied and Claude access was disabled. Continue the existing read-only hourly error-log monitor.
- **Rollback:** revert PR #31 and redeploy only the two GenLead processes. The extra trailing SearchRuns column is harmless if retained; there is no prospect-row migration to reverse.
